从 Spring Boot 的视角理解 MCP

做 Agent 开发的同学最近一定被 MCP 刷屏了。但网上的 MCP 教程大多是 Python 和 TypeScript 视角，作为写了 6 年 Spring Boot 的 Java 工程师，我一开始看那些文档也是一头雾水——直到我意识到一件事：

MCP 本质上就是”给 LLM 用的接口协议”，而你写 REST 接口的经验可以直接平移过来。

这篇文章就用 Spring 的概念把 MCP 拆开讲，十分钟应该能看懂。

一、MCP 是什么（30 秒版）

MCP（Model Context Protocol）是 Anthropic 提出的一个开放协议，目的是让 AI 应用统一地接入工具和数据源。

打个比方：以前给 AI 接一个工具，要做一套私有对接；接十个工具，要做十套。MCP 把这些统一成一个标准接口——就像 USB-C 统一了各种充电口，MCP 统一了”AI 接工具”这件事。

  • MCP Server：提供工具和数据的一方（比如”Git 操作工具””数据库查询工具”）。
  • MCP Client：连接 LLM 和 Server 的一方（比如 Claude Code、Cursor 这些客户端）。
  • 协议：双方通信的语言规范。

二、用 Spring 的类比拆解 MCP

下面这张对照表是我自己的理解方式，也是全文的核心：

Spring 概念 MCP 概念 对应关系
@RestController MCP Server 暴露能力的一方
@GetMapping("/xxx") 接口 Tool 一个可被调用的能力
Spring 容器 MCP Client 管理、调用这些能力
Bean 注入（@Autowired） Tool 注册 把能力交给调用方使用
参数对象 + @Validated 校验 JSON Schema 参数声明 定义”调用时要传什么”
OpenAPI / Swagger 文档 MCP 的 tools/list 元数据 告诉调用方”有哪些接口”
微服务之间的 RPC 调用 Client ↔ Server 通信 跨进程调用
配置文件（application.yml） MCP 配置文件 配置连接哪些 Server

如果你写过 REST 接口，其实你已经掌握了 MCP Server 的全部核心概念。区别只是：

  • REST 是人或者前端调你的接口；
  • MCP 是大模型通过 Client 调你的 Tool。

接口的写法、参数的声明、文档的维护——这些你早就熟得不能再熟了。

三、MCP 的三类核心角色

再深入一点，MCP 协议里定义了三种”资源”：

角色 作用 Spring 类比
Tools 可执行的函数（有副作用，比如”创建订单”） Controller 里的写接口
Resources 可读取的数据（比如”数据库里的配置”） Service 层查询 + 返回数据
Prompts 预置的提示词模板（给 LLM 用的”剧本”） 模板方法 / 策略配置

对新手来说，先盯住 Tools 就够了，90% 的场景都是”给模型加一个能调的工具”。

四、一个 MCP Server 长什么样

下面用一个最小示例感受一下。以官方 Python SDK 为例（Java 也有官方 SDK io.modelcontextprotocol.sdk，这里选 Python 是因为它最简洁、最接近官方文档，理解结构即可）：

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """查询指定城市的天气"""
    # 这里可以接真实天气 API
    return f"{city} 今天晴，25°C"

@mcp.tool()
def get_stock(code: str) -> str:
    """查询股票价格"""
    return f"{code} 当前价格 99.8"

就这么简单。一个 @mcp.tool() 装饰的函数，就是一个 Tool。

它和 Spring 里下面的代码，几乎是一一对应的：

@RestController
@RequestMapping("/weather")
public class WeatherController {

    @GetMapping
    public String getWeather(@RequestParam String city) {
        return city + " 今天晴，25°C";
    }
}

唯一的区别：@GetMapping 是让浏览器/前端调的，@mcp.tool() 是让大模型调的。你写的每个 Tool，背后都要声明一份 JSON Schema，告诉模型”这个函数要什么参数、返回什么”，跟 Swagger 给前端看接口文档一个道理。

五、怎么接入一个现成的 MCP Server

接入一个 MCP Server，对 Java 工程师来说，感觉就像”Maven 引入依赖 + 配置文件里加一段数据源”。

以 Claude Code 为例，在配置文件里加一段：

{
  "mcpServers": {
    "git": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-git"]
    }
  }
}

保存后，Claude 就能调用这个 Server 暴露的所有 Git 工具了。整个过程你不需要写一行业务代码，只需要”声明我连了哪个 Server”，跟你在 application.yml 里配一个数据源几乎一模一样。

作为 Java 工程师，你更容易反过来想：与其等着别人写好 MCP Server，不如把你公司内部的系统包装成 MCP Server——给 AI 暴露”查询订单””创建工单”这些 Tool，让 Agent 直接接管你已有的业务能力。

六、为什么这对 Java 开发者是好消息

  1. 技能直接平移：接口设计、参数校验、文档维护、版本兼容——MCP Server 的开发全是你六年练过的基本功。
  2. 企业落地是刚需：现在真正的需求不是”写个 Demo”，而是”把公司内部系统安全地接给 AI”。谁来做？后端工程师。这个活本来就是你的，只是换了个协议。
  3. 稀缺性：会写 MCP Server 的人里，能考虑权限、鉴权、日志、限流这些生产问题的，基本都是后端出身。Java 工程师做这个，是降维打击。

七、总结与下一步

  • MCP = 给 LLM 用的接口协议，Server / Client / 协议三件套，你写 REST 的经验直接平移。
  • 一个 MCP Server 就是一堆 @mcp.tool() 函数，和 @RestController 一一对应。
  • 接入现成 Server 约等于”Maven 引依赖 + 配数据源”。
  • 对 Java 工程师来说，MCP 是”让 6 年经验继续值钱”的技术，而不是要推倒重来的新东西。

下一步建议：别只读文章。挑一个你熟悉的内部 API（比如查询订单），用 SDK 把它包成一个 MCP Server，再让 Claude 调用一次试试。跑通的那一刻，你会觉得这玩意儿亲切得像老朋友。
