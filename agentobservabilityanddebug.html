Agent 也是"系统"：聊聊可观测性与 Debug

写 Demo 的 Agent 谁都会做，难的是把它稳定地跑在生产里。

我做过几年 Spring Boot 微服务，一开始调试 Agent 的时候非常不适应：以前线上出问题，看日志、看链路、看指标，三步定位；现在 Agent 出问题，我连”它到底干了什么”都不知道。后来我想明白一件事——我把 Agent 当成了”魔法”，而它其实只是个”系统”。

系统就该用系统的方法来观测。这篇文章聊聊我是怎么把后端那套”日志、链路、指标”三板斧搬到 Agent 开发上的。

一、为什么 Agent 这么难调

传统后端和 Agent 的调试难度，根本不在一个量级。原因有四个：

  1. 非确定性：同样的输入，可能得到不同的输出。复现一个 bug 都难。
  2. 黑盒：模型内部怎么”思考”的，你基本看不到，只能从输入输出猜。
  3. 多步状态：一个任务拆成很多步，状态散落在每一步里，错一步后面全歪。
  4. 副作用：一次错误的工具调用，可能真的改了数据、发了消息，损失是真金白银。

所以调试 Agent 的第一原则是：不要在脑子里”复盘”，要让系统把过程”记下来”。

二、把 Agent 当系统：三板斧一样不少

后端有日志、链路、指标，Agent 也需要这三样，只是对象变了：

维度 传统后端 Agent
日志（Logs） 请求参数、异常堆栈 每次模型调用的输入、输出、耗时
链路（Traces） 一次请求跨服务的调用链 一个 Agent 任务里的步骤链：思考、工具调用、结果
指标（Metrics） QPS、RT、错误率 token 消耗、任务成功率、平均步数

三、从零开始记日志：结构化是第一位的

Agent 的日志，最忌讳用 print 一坨糊在控制台。要像记业务日志一样，每条都结构化，带上足够的上下文字段，否则事后根本没法查。

我自己记 Agent 日志，最少包含这些字段：

{
  "timestamp": "2026-08-03T10:30:00Z",
  "request_id": "req_8f3k2a",
  "session_id": "sess_01",
  "step": 3,
  "type": "tool_call",
  "tool": "search_orders",
  "tool_input": {"order_id": "A1001"},
  "tool_output": "订单状态: 已发货",
  "latency_ms": 120,
  "tokens": 842
}

几个关键设计：

  • request_id / session_id：把一次任务的每一步串起来，这是排查的基础，类比 Spring 里的 traceId。
  • step：记录这是第几步，方便看出”卡在哪一步”。
  • type：区分是 model_call、tool_call、tool_result、error，一眼看清流程。
  • tokens：记录 token 消耗，成本出问题时能追溯。

一个小技巧：Java 里用 SLF4J + Logstash 格式，或者直接用 JSON 序列化一条日志，都能轻松做到结构化。你把 Agent 调用当成一个普通 Service 的日志来记，就对了。

四、一次 Debug 实录

拿我真实踩过的一个坑举例：一个基于 RAG 的文档问答 Agent，问”我们的退款政策是多久”，它回答错。

我按流程排查：

第 1 步：看最终输入输出。 问题很简单，不是 prompt 问题。

第 2 步：看 trace，数一下步骤。 发现它只做了 4 步：检索 → 组装 → 调用模型 → 回答。看起来正常。

第 3 步：看检索那一步的工具输出。 发现检索出来的 3 篇文档里，没有一篇是讲退款政策的——问题根本不在模型，在检索到的内容不对。

第 4 步：定位到向量化的切分策略。 退款政策这一节太短，被并进了相邻的章节，导致按语义检索时召回不到。

第 5 步：修切分逻辑 + 加一条回归用例。 再问同样的问题，答对了。

这个案例的核心教训是：没有 trace，我根本不知道错在哪一步，大概率会去瞎改 prompt，越改越错。而有了结构化日志，30 秒就定位到了根因。

五、Agent 常见故障模式与排查清单

踩的坑多了，我整理了一张对照表，排查时直接对号入座：

故障模式 现象 常见原因 排查点 对策
死循环（Loop） 同一个工具反复调用 模型认为任务没完成，不停重试 trace 里工具名重复出现 设步数上限、超时、结果校验
工具滥用 频繁调无关工具 工具说明写得太模糊 统计各工具调用次数 写清”何时不用”，加频控
幻觉 / 编造 回答了不存在的数据 数据缺失时模型自行脑补 看输出里有没有”来源” 要求引用来源，缺失就报 no_data
上下文溢出 长任务后行为异常 上下文塞满，早期信息被截断 tokens 字段持续飙高 压缩、改用检索、精简上下文
多轮状态丢失 前后回答对不上 状态存在对话里，被截断/遗忘 session 内多个 step 上下文对比 显式状态管理、写入外部存储

六、现成工具：别重复造轮子

自己记结构化日志是最低门槛的做法，但等 Agent 多了，还是建议用现成的可观测性平台，比如 LangSmith、Langfuse、Helicone 这些。

它们的核心能力就是帮你把”模型调用、工具调用、token 消耗”自动记录下来，还能可视化地看到整条 trace，甚至回放。

我的建议：

  • 前期：先自己记 JSON 日志，养成”每一步都要可追踪”的意识。
  • 后期：接入现成平台，把 trace、评测、成本管理都收拢到一处。

用什么工具不重要，先有 trace 意识才重要。

七、Java 经验迁移：你早就练过这些

写到这里你会发现，这一切对你来说并不陌生：

  • SLF4J 结构化日志 → Agent 的结构化日志；
  • Micrometer / Prometheus 指标 → token、成功率、平均步数；
  • 分布式链路追踪（Sleuth / Micrometer Tracing） → Agent 的 step trace。

它们只是把”服务”换成了”模型调用”，把”接口”换成了”Tool”。你六年积累的这套工程化习惯，在 Agent 时代反而是稀缺能力——大多数写 Agent 的人没有系统运维的经验，恰恰缺的就是这个。

八、总结

  • Agent 不是魔法，是系统。系统的调试，靠日志、链路、指标三板斧。
  • 日志必须结构化，request_id + step + type + tokens 是最低配置。
  • 排查要”看过程”而不是”猜答案”：trace 会告诉你错在哪一步。
  • 常见的故障模式（死循环、工具滥用、幻觉、上下文溢出）都可以对表排查、提前预防。
  • 你已有的后端工程经验，是调试 Agent 的最大武器，别把它丢掉。
